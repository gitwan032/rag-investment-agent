# 설계 검증 기록: 팀 설계의 가정 vs 개인 구현의 측정 결과

팀 산출물(2026-09-30)의 설계를 그대로 따르지 않고, 각 선택이 우리 데이터에서도 맞는지 직접 측정한 뒤 결정했다.
아래는 **팀의 가정, 나의 예상, 실제 결과가 서로 달랐던 지점**과 그에 따른 결정이다.

- 평가셋: 기술 문서 20문항, 시장 보고서 30문항 (한국어 질문 → 정답 문서·쪽)
- 지표: Hit Rate@5 (상위 5개 안에 정답 포함 비율), MRR (정답 순위 역수의 평균)
- 측정 코드: `eval/retriever_eval.py`, 원본 결과: `outputs/retriever_eval.md`, `outputs/chunking_eval.md`

## 변경 원칙: 무엇을 바꾸고 무엇을 지켰나

팀 설계의 뼈대는 유지하고, 다음 세 가지 근거 중 하나가 있을 때만 바꿨다. 근거 없이 바꾼 것은 되돌렸다.

1. **측정 결과**: 같은 평가셋(50문항)으로 비교해 수치가 더 좋았다
2. **팀 보고서의 실제 문제**: 제출된 팀 보고서에서 확인된 문제를 고치기 위해
3. **과제 원칙·실행 중 발견**: "복사가 아니라 이해하며 다시 만든다", 실행하면서 드러난 오류

## 1. 청킹: "토큰으로 정확히 재면 더 좋을 것이다" → 틀렸고, 진짜 변수는 크기였다

| 구분 | 내용 |
|---|---|
| 팀의 방식 | 설계값 "약 800토큰"을 글자 수로 어림 (영어 3,000자, 한국어 1,200자) |
| 나의 예상 | bge-m3 토크나이저로 실제 800토큰을 재면 설계와 정확히 일치하므로 같거나 더 좋을 것 |
| 실제 결과 | 같은 800토큰 목표에서는 팀 방식이 더 좋았다. 크기를 400토큰으로 줄이자 가장 좋아졌다 |

| 청킹 (Dense 검색) | 기술 Hit@5 | 기술 MRR | 시장 Hit@5 | 시장 MRR | 청크 수 (기술 / 시장) |
|---|---:|---:|---:|---:|---:|
| 팀: 글자 수 (영 3,000 / 한 1,200자) | 0.850 | 0.702 | 0.867 | **0.672** | 231 / 84 |
| 토큰 800 / overlap 100 (처음 설정) | 0.800 | 0.629 | 0.867 | 0.654 | 192 / 69 |
| 토큰 600 / overlap 75 | 0.850 | 0.668 | 0.833 | 0.646 | 239 / 94 |
| **토큰 400 / overlap 50 (최종)** | **0.950** | **0.863** | 0.867 | 0.648 | 332 / 124 |

**원인**: 차이는 "토큰 vs 글자"가 아니라 **청크 크기**였다. 영어 3,000자는 bge-m3 토큰으로 800보다 작아서 팀 방식이 더 잘게 잘렸다(231개 vs 192개). 청크가 크면 한 청크에 여러 주제가 섞여 질문과의 유사도가 흐려진다. 크기를 줄일수록 기술 문서 성능이 뚜렷하게 올랐다(MRR 0.629 → 0.668 → 0.863).

**결정**: 토큰 기준을 유지하고 **400토큰 / overlap 50**으로 바꾼다.

- 기술 문서는 팀 방식보다 크게 좋다 (Hit 0.850 → 0.950, MRR 0.702 → 0.863).
- 시장 보고서는 팀 방식과 거의 같다 (Hit 동일, MRR 0.672 vs 0.648로 1문항 미만의 순위 차이).
- 50문항 전체 평균: Hit 0.860 → 0.900, MRR 0.684 → 0.734.

**한계**: 400토큰보다 작은 크기는 시험하지 않았다. 청크가 작을수록 LLM에 전달되는 문맥이 짧아지므로, 생성 단계에서 문맥이 부족하면 검색 개수(k)를 늘려 보완한다.

## 2. 하이브리드 검색: "BM25를 섞으면 좋아진다" → 우리 데이터에서는 나빠졌다

| 구분 | 내용 |
|---|---|
| 팀의 설계 | 시장성 평가에 BM25 + Dense를 RRF로 결합 (수업 실습에서도 Ensemble이 MRR 1위) |
| 실제 결과 | BM25를 섞자 Dense 단독보다 순위가 나빠졌다 (800토큰, 400토큰 모두 같은 경향) |

| 검색기 (400토큰) | 기술 Hit@5 | 기술 MRR | 시장 Hit@5 | 시장 MRR |
|---|---:|---:|---:|---:|
| Dense (bge-m3) | 0.950 | 0.863 | 0.867 | 0.648 |
| BM25 (Kiwi) | 0.300 | 0.242 | 0.400 | 0.286 |
| Ensemble (BM25 + Dense) | 0.900 | 0.527 | 0.667 | 0.467 |

**원인**: 질문은 한국어, 문서는 대부분 영어라서 키워드가 거의 겹치지 않는다(어휘 불일치). 수업 실습은 질문과 문서가 같은 언어여서 BM25가 도움이 됐지만, 교차언어 환경에서는 BM25가 엉뚱한 청크를 끌어올려 Dense의 좋은 순위를 흐린다.

**교훈**: 수업에서 가장 좋았던 기법도 데이터 조건(언어)이 다르면 결과가 뒤집힌다. 기법은 측정 후에 고른다.

## 3. 리랭커: "시장성에만 필요하다" → 기술 요약에도 효과가 가장 컸다

| 구분 | 내용 |
|---|---|
| 팀의 설계 | 리랭커는 시장성 평가(Advanced RAG)에만 적용, 기술 요약은 Dense Top-5 + LLM 관련성 판정·질의 재작성 루프 |
| 실제 결과 | 리랭커가 기술·시장 모두에서 가장 큰 개선 |

| 검색기 (400토큰) | 기술 Hit@5 | 기술 MRR | 시장 Hit@5 | 시장 MRR | 질문당 시간 |
|---|---:|---:|---:|---:|---:|
| Dense (bge-m3) | 0.950 | 0.863 | 0.867 | 0.648 | 0.03초 |
| Dense + Reranker | **0.950** | **0.925** | **0.967** | **0.844** | 1.95초 |

BM25를 섞으면 순위가 나빠졌지만, 리랭커가 후보 20개를 질문과 함께 다시 읽고 정리하자 정답이 거의 항상 1등에 왔다. 처음 설정(800토큰)에서는 기술 MRR이 0.629 → 0.900, 최종 설정(400토큰)에서는 0.863 → 0.925로 올랐다. 대신 질문당 약 2초가 걸린다. 에이전트는 기업당 질문 몇 개만 던지므로 감당할 수 있는 수준이다. 청크가 작아지면서 리랭커가 읽을 글이 줄어 시간도 800토큰 때(4~6초)보다 짧아졌다.

**의미**: 리랭커로 처음부터 정답을 상위에 올리면, 기술 요약의 Agentic RAG 루프(관련성 판정 → 질의 재작성)가 덜 돌게 되어 LLM 호출 비용도 줄어든다.

### 3-1. "BM25가 한국어 문서 후보를 보탠다"는 추정 → 재측정에서 사라졌다

| 리랭커 앞단 후보 | 800토큰 시장 Hit / MRR | 400토큰 시장 Hit / MRR |
|---|---:|---:|
| Dense만 | 0.933 / 0.786 | 0.967 / 0.844 |
| BM25 + Dense | 0.967 / 0.814 | 0.967 / 0.844 |

800토큰 인덱스에서는 BM25를 섞은 쪽이 시장 문항을 1개 더 맞혀서, "한국어 보고서(포스코경영연구원)가 있으니 BM25가 Dense가 놓친 후보를 보탠다"고 해석했다. 그런데 400토큰으로 다시 만들자 두 조합의 결과가 **완전히 같아졌다.**

**결론**: 그 1문항 차이는 청크 경계에 따라 생긴 우연이었고, BM25가 후보를 보태는 효과는 확인되지 않았다. 30문항 중 1문항 차이는 근거가 되지 못한다는 것, 그리고 설정을 바꿔 다시 재 보기 전에는 해석을 확정하면 안 된다는 것을 배웠다.

**결정**:

| 에이전트 | 검색기 | 근거 |
|---|---|---|
| 기술 요약 | Dense + Reranker | 가장 정확하고 단순함 |
| 시장성 평가 | Dense + Reranker | BM25를 섞어도 같은 결과이고, 더 빠름 (3.13초 → 1.95초) |

팀은 시장성 평가에 BM25 하이브리드를 설계했지만, 우리 데이터(한국어 질문, 영어 중심 문서)에서는 BM25가 순위를 개선하지도, 후보를 보태지도 못했다. 그래서 BM25를 빼고 구조를 단순하게 했다.

## 4. 임베딩 모델: 팀 결론 재확인

팀이 3개 모델 비교로 고른 BAAI/bge-m3를 그대로 사용했다. 같은 모델로 다시 측정한 Dense 결과(800토큰: 기술 0.800 / 0.629, 시장 0.867 / 0.654)는 팀 측정값(기술 0.800 / 0.627, 시장 0.800 / 0.612)과 같거나 높아, 선택이 유효함을 확인했다. 다른 임베딩 모델은 다시 비교하지 않았다.

### 5-1. 판정 기준: 내가 엄격하게 바꾼 기준이 문서를 모두 떨어뜨렸다 → 팀 기준으로 되돌림

| 구분 | 내용 |
|---|---|
| 처음 관찰 | 팀 질문 "{분야} AI 기술의 업계 수준과 상용화 단계(TRL 판단 근거)는?"으로 Agentic RAG를 돌리자, 3번 검색·2번 재작성 동안 기술 문서가 하나도 통과하지 못하고 웹 보완으로 넘어갔다 |
| 바로잡은 사실 | 이 실행은 팀 판정 기준이 아니라 **내가 처음 작성한 더 엄격한 판정 프롬프트**("핵심에 직접 쓸 내용이 없으면 false")로 돌린 결과였다. 팀 원문 판정 기준으로 되돌리자 같은 질문에서 기술 문서가 통과했다 |
| 교훈 | 문서가 쓰이지 않은 원인을 "질문이 문서에 맞지 않는다"고 추정했지만, 실제 원인은 내가 바꾼 판정 기준이었다. 근거 없이 바꾼 기준이 결과를 왜곡할 수 있다 |
| 결정 | 판정 프롬프트, 통과 기준(관련 문서 2개), 재작성 최대 2회는 팀 원문을 유지한다 |

### 5-2. 질문 방식: 팀 원문 한 문장 vs 두 질문으로 분해 (`eval/rag_question_eval.py`)

판정 기준은 둘 다 팀 원문. 분해 질문은 수업 3장 Query Transformation을 적용해 같은 목적을 ① 상용화 단계 ② 성능 개선 수치 두 질문으로 나눴다.

| 분야 | 팀 질문: 통과 문서 | 재작성 | 웹 보완 | 분해 질문: 통과 문서 | 재작성 | 웹 보완 |
|---|---:|---:|:---:|---:|---:|:---:|
| 전력 수요 예측 | 1 | 2 | 예 | 4 | 2 | 예 |
| 발전 예측·VPP | 2 | 0 | 아니오 | 4 | 2 | 예 |
| 배터리(ESS) 운영 | 3 | 0 | 아니오 | 6 | 2 | 예 |
| 전력망 관리 | 4 | 0 | 아니오 | 4 | 2 | 예 |
| **합계** | **10** | | | **18** | | |

원본 결과: `outputs/rag_question_eval.md` (2026-10-14 측정)

| 구분 | 내용 |
|---|---|
| 나의 예상 | 질문을 나누면 각 질문이 문서의 특정 부분과 더 잘 맞아 더 많은 기술 문서가 통과할 것이다 |
| 결과 | 통과 문서는 분해 질문이 많았다 (18개 vs 10개). 하지만 **4개 분야 모두 두 질문 중 하나가 재작성 2회를 다 쓰고 웹 보완까지 갔다**. 특히 "성능 개선 수치" 질문은 정책·동향 보고서 위주인 문서에 맞는 내용이 적었다. 팀 질문은 4개 중 3개 분야에서 재작성 없이 첫 검색에 기준(2개)을 넘겼다 |
| 결정 | **팀 원문 질문 유지.** 기술 요약에서 이 RAG의 역할은 TRL 판단의 업계 기준선이고 회사 고유 정보는 웹 검색이 맡으므로, 기준 충족(2개)이면 충분하다. 분해 질문은 질문 수가 두 배이고 매번 재작성·웹 보완까지 가서 LLM 호출과 검색 비용이 크게 늘어난다. 팀 판정 기준을 지킨다는 원칙과도 맞다 |
| 남은 약점 | 전력 수요 예측은 팀 질문으로 1개만 통과해 웹 보완에 의존한다 (`python app.py` 실행에서도 같은 결과). 판정 모델은 temperature를 고정할 수 없어(GPT-5 계열) 경계에 있는 문서는 실행마다 판정이 달라질 수 있다. 개선안: 팀 질문이 기준에 못 미칠 때만 분해 질문으로 한 번 더 찾는 방식 (미구현) |
| 기록 | 측정 후 정리 과정에서 측정 스크립트를 실수로 지웠다가 같은 방식·같은 출력 형식으로 다시 작성했다 |

### 5-3. 코드 보정 1건

팀 재작성 프롬프트의 "모르면 '공개 정보 부족'이라고 적어라" 규칙 때문에, 새 검색어 끝에 "공개 정보 부족"이 붙어 검색을 흐리는 경우가 실행 로그에서 확인됐다. 프롬프트는 팀 원문 그대로 두고, 코드에서 이 문구만 검색어에서 지운다 (`rag/agentic_rag.py`의 rewrite).

## 6. 판정 일관성: "temperature를 고정하면 흔들림이 사라진다" → 흔들림의 주원인은 판정 모델이 아니었다

| 구분 | 내용 |
|---|---|
| 관찰 | 같은 질문(전력 수요 예측)에서 통과한 기술 문서가 실행마다 2 → 1 → 0 → 2개로 달라졌다. 같은 기업(Amperon) 총점도 실행마다 달랐다: 72.3 → 74.7 → 79.1점 (판정은 모두 투자). 단, 첫 실행(72.3점) 뒤에 채점·경쟁사 프롬프트를 고쳤으므로 **같은 코드로 비교할 수 있는 것은 2·3회차(74.7 vs 79.1점)뿐**이다 |
| 나의 예상 | 판정 모델을 추론 강도 `low`로 호출해 temperature를 지정할 수 없는 것이 원인이다. 팀 설계대로 temperature 0으로 고정하면 흔들림이 사라질 것이다 |
| 측정 | 입력을 고정하고 두 설정으로 3번씩 판정했다 (`eval/consistency_eval.py`, 원본 `outputs/consistency_eval.md`). ① 4개 분야 질문의 검색 문서 5개 관련성 판정 ② 같은 채점 입력(Amperon)으로 투자 채점 |

**① 문서 관련성 판정 (같은 문서 5개, 3회)**

| 분야 | `low` 통과 수 | `none` + temp 0 통과 수 |
|---|---|---|
| 전력 수요 예측 | 0 / 0 / 0 | 2 / 2 / 2 |
| 발전 예측·VPP | 2 / 2 / 2 | 2 / 2 / 2 |
| 배터리(ESS) 운영 | 3 / 3 / 3 | 5 / 5 / 5 |
| 전력망 관리 | 4 / 4 / 4 | 3 / 4 / 3 |
| 판정이 바뀐 문서 | 0 / 20 | 1 / 20 |

**② 투자 채점 (같은 채점 입력, 3회)**

| 설정 | 총점 | 범위 | 점수가 바뀐 항목 |
|---|---|---:|---:|
| `low` | 77.2 / 77.5 / 77.2 | 0.3 | 8 / 11 |
| `none` + temp 0 | 76.9 / 78.9 / 76.9 | 2.0 | 3 / 11 |

| 구분 | 내용 |
|---|---|
| 결과 1: 일관성 차이는 거의 없다 | 연속 3회 반복에서는 두 설정 모두 거의 같은 판정을 냈다. 총점 범위는 `low`가 좁았지만 항목 점수는 `low`가 더 많이 바뀌었다(서로 상쇄되어 총점만 비슷). 어느 쪽이 더 일관적이라고 할 수 없다 |
| 결과 2: 연속 반복은 흔들림을 덜 보여준다 | 측정 몇 분 전 `python app.py` 실행에서는 같은 문서 5개 중 2개가 `low`로 통과했고(WEF p.9, p.10), 같은 채점 입력의 총점은 79.1점이었다. 즉 같은 설정·같은 입력이라도 시간 간격을 두면 결과가 달라질 수 있고(약 ±2점), 연속 3회 측정은 이를 과소평가한다 |
| 결과 3: 두 설정은 엄격함이 다르다 | `none`이 문서를 더 많이 통과시켰다 (전력 수요 예측 0 → 2개, ESS 3 → 5개). 일관성이 아니라 판정 기준의 엄격함 차이다 |
| 결과 4: 실행 간 총점 차이의 주원인은 판정 모델이 아니다 | 같은 코드·같은 설정(`low`)으로 비교하면 차이가 두 층으로 나뉜다. **같은 채점 입력을 다시 채점**했을 때는 77.2 ~ 79.1점(4회, 범위 1.9점)이었고, **전체를 다시 실행**했을 때는 74.7 vs 79.1점(4.4점)이었다. 웹 검색은 캐시로 같은 결과를 쓰므로, 판정 모델 몫을 뺀 나머지는 앞 단계에서 온다. 실제로 2회차에서는 기술 문서가 0개 통과해 기술 요약이 웹 근거로만 쓰였고, 3회차에서는 2개가 통과했다. 앞 단계(생성 모델의 분석 문장, 통과 문서)가 달라지면 채점 입력 자체가 달라지고, 그 차이가 최종 점수까지 이어진다 |
| 결정 | 판정 모델을 **팀 설계대로 temperature 0(`none`)**으로 되돌린다. `low`는 내가 측정 없이 바꾼 설정이었고, 측정에서 일관성 이점이 확인되지 않았으므로 "근거 없이 바꾼 것은 되돌린다"는 원칙을 적용했다. 이 설정에서 팀 질문이 4개 분야 모두 판정 기준(2개)을 넘었다 |
| 최종 실행 (`none` + temp 0) | 전력 수요 예측 질문에서 기술 문서 2개(WEF p.9, p.10)가 재작성 없이 통과했고, WEF 보고서가 REFERENCE에 기관 보고서로 실렸다. Amperon 75.3점, 투자 추천 (`outputs/report_20261014_162853.pdf`) |
| 새로 clone한 재현성 실행 | 벡터스토어·검색 캐시가 없는 상태에서 `python app.py` 한 번으로 인덱스 생성(332 + 124청크)부터 보고서까지 완료했다. 검색 캐시가 없어 웹 검색 결과가 달라졌고 후보 구성도 달라졌다(ThinkLabs AI, GridBeyond, Dexter Energy 등). 같은 질문에서 기술 문서 2개(WEF p.9, p.10)가 다시 통과했고, Amperon은 **70.7점으로 기준(70점)을 0.7점 넘겨 투자**였다. 같은 설정에서도 75.3점과 70.7점으로 갈려, 기준선 근처에서는 실행마다 판정이 바뀔 수 있음을 보여준다 |
| 남은 한계 | temperature 0도 결과를 완전히 고정하지 못한다. 실행 간 차이를 줄이려면 생성 결과(기술 요약 등)를 캐시해 같은 입력으로 다시 채점할 수 있게 하거나, 채점을 여러 번 해 평균을 내야 한다 (미구현). 판정이 기준선(70점) 근처일 때는 실행마다 투자/보류가 바뀔 수 있다 |

## 7. 남은 한계와 개선 과제

팀 산출물을 검토한 것과 같은 기준으로 내 결과물을 다시 검토했다.

| 한계 | 내용 | 개선 방향 |
|---|---|---|
| 근거 번호 ≠ 근거 내용 | 코드는 주장에 유효한 근거 번호 `[n]`이 달렸는지만 확인한다. 내용이 실제로 원문에 있는지 대조하는 것은 시장 수치(원문 인용 검증)뿐이다. 예: 창업팀 점수(가중치 25)의 근거가 된 "공동창업자의 여러 회사 엑싯 경험"은 원문 대조를 거치지 않았다 | 점수에 큰 영향을 주는 사실(창업팀 경력, 고객 수, 투자 유치)에도 원문 인용 검증을 넓힌다 |
| 같은 평가셋으로 선택하고 보고 | 청크 크기·검색기를 50문항으로 고른 뒤 최종 성능도 같은 50문항으로 보고했다. 따로 떼어 둔 검증 문항이 없어 수치가 실제보다 좋게 나왔을 수 있다 | 평가셋을 선택용·보고용으로 나눈다 |
| 작은 표본 | 기술 문서 20문항이라 MRR 0.863 → 0.925는 1~2문항 차이다. 3-1에서 "30문항 중 1문항 차이는 근거가 되지 못한다"고 쓴 교훈이 내 결과에도 그대로 적용된다 | 문항을 늘리거나, 리랭커 효과를 여러 설정에서 반복 확인한다 |
| 검색만 평가 | Hit Rate·MRR은 검색 단계만 잰다. 최종 보고서의 문장이 근거와 맞는지(생성 품질)는 평가하지 않았다 | 보고서 주장 표본을 뽑아 근거와 대조하는 평가를 추가한다 |
| 문서 구성 | 문서 6종은 팀 선정을 그대로 썼다. 실제 실행에서 시장 수치는 DOE VPP 보고서 한 종에서만 나왔고(미국 전력 수요 등 인접 시장 수치), 수요 예측 소프트웨어 시장 규모를 다루는 문서는 없다. IEA·포스코경영연구원 보고서는 두 번의 실행에서 쓰이지 않았다 | 분야별 시장 규모를 다루는 보고서를 추가하고, 문서별 사용 빈도를 확인한다 |
| 실행마다 다른 후보 순서 | 웹 검색 결과가 달라 후보 순서가 바뀐다 (1회차 Amperon 먼저, 2회차 Capalo AI 먼저) | 실행 결과(후보 목록)를 저장해 같은 후보로 다시 평가할 수 있게 한다 |
| 웹 출처 날짜 | 검색 도구가 게시일을 거의 주지 않아 웹 출처 대부분이 조회일로 표기된다 (보고서에 명시) | 페이지 본문에서 게시일을 추출한다 |
